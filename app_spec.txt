Omnismi Project Spec
====================

Project type
- Omnismi is a Python library, not a web app or long-running service.
- Anthropic-style harness rules still apply, but `init.sh` should bootstrap the package and run validation instead of starting a server.

Product goal
- Provide a compact, stable, cross-vendor accelerator observability API for AI agents and Python applications.
- Current in-scope accelerators are NVIDIA GPUs, AMD GPUs, and experimental Google TPUs.
- Long-term expansion should add more vendors without breaking the public API contract.

Primary users
- Coding agents that need portable accelerator preflight checks.
- Python applications that need normalized accelerator inventory and metrics.
- Contributors validating vendor/runtime parity against ground-truth libraries.

Current public contract
- Top-level API: `omnismi.count()`, `omnismi.gpus()`, `omnismi.gpu(index)`.
- Device object: `GPU.index`, `GPU.info()`, `GPU.metrics()`, `GPU.realtime()`.
- Public models: `GPUInfo`, `GPUMetrics`.
- Supported public vendors today: `nvidia`, `amd`, `google`.
- `GPU` / `gpus()` names are historical API names and currently also cover the experimental Google TPU backend.

Public model fields
- `GPUInfo`: `index`, `vendor`, `name`, `uuid`, `driver`, `memory_total_bytes`.
- `GPUMetrics`: `index`, `utilization_percent`, `memory_used_bytes`, `memory_total_bytes`, `temperature_c`, `power_w`, `core_clock_mhz`, `memory_clock_mhz`, `timestamp_ns`.

Hard invariants
- Public API names stay minimal and stable. Do not introduce `get_*` aliases.
- `utilization_percent` means vendor-reported top-level compute/graphics engine activity. Do not relabel it as SM occupancy or CU occupancy.
- Fixed normalized units: bytes, percent, Celsius, Watts, MHz.
- Unavailable metrics default to `None` instead of raising in normal user flows.
- Backend-specific exceptions must not leak through the default public API path.
- Backend implementation details stay out of user-facing API docs unless required for compatibility notes.
- Vendor onboarding must preserve the existing `count/gpus/gpu` and `info/metrics` contract.

Current backend behavior
- NVIDIA uses `nvidia-ml-py` (`pynvml`) and supports cached psutil-style sampling plus `GPU.realtime()` for forced live reads.
- AMD uses `amdsmi` with compatibility fallbacks for handle discovery, temperature, power, and clocks, plus cached psutil-style sampling and `GPU.realtime()`.
- Google TPU uses `libtpu.sdk.tpumonitoring` for local snapshot metrics such as duty cycle and HBM usage. Temperature, power, clocks, and parity tooling are still unavailable.
- The backend registry instantiates known backends lazily, filters unavailable ones, and closes them at process exit.

Validation contract
- Baseline automated check: `PYTHONPATH=src pytest -q`.
- Import/build smoke check: `python -m compileall src tests`.
- Optional hardware parity checks:
  - `PYTHONPATH=src python -m omnismi.validation.parity --vendor nvidia --samples 3`
  - `PYTHONPATH=src python -m omnismi.validation.parity --vendor amd --samples 3`
- Public-facing changes must update tests and docs in the same session.

Current non-goals
- Reintroducing runtime dependency installers or legacy 0.x APIs.
- Expanding the public API with scheduler/framework-specific helpers before the core contract is stable.
- Hiding platform/runtime limitations behind fake values.

Environment compatibility goals
- Discovery and diagnostics should work on supported GPU hosts, GPU containers,
  and Kubernetes device-plugin environments without pretending the process can
  see more devices than the current runtime actually exposes.
- Discovery and diagnostics should surface runtime visibility controls such as
  `CUDA_VISIBLE_DEVICES`, `NVIDIA_VISIBLE_DEVICES`, `ROCR_VISIBLE_DEVICES`, and
  related environment scoping when those controls affect what the process can see.
- For supported GPU vendors, if the current runtime can enumerate visible GPUs,
  Omnismi should aim to expose the same visible logical device set in the
  discovery layer, or explain mismatches clearly through diagnostics.

Planned frontier
- More hardware validation evidence for existing NVIDIA and AMD adapters.
- Better backend diagnostics and debug visibility.
- A default `omnismi` CLI experience that gives a modern, cross-vendor machine
  summary similar in spirit to `nvidia-smi`, but cleaner and more
  automation-friendly.
- The main CLI entry should be human-first by default: concise terminal summary
  first, explicit `json`/`yaml` output on demand, and deeper detail moved into
  `--wide`, `doctor`, `bench`, and `validate-spec`.
- CLI-first machine profile and spec-validation workflows that can confirm whether
  detected hardware matches expected capacity, bandwidth, and throughput classes.
- The first `validate-spec` slice should stay discovery-first: compare current
  inventory against curated profiles and explicit runtime context now, then add
  benchmark evidence later without breaking the report shape.
- Vendor-agnostic benchmark probes for trustable memory-bandwidth and compute
  sanity checks, kept separate from vendor sample applications.
- The first benchmark slice should prioritize a portable `bandwidth` probe with
  stable `table/json/yaml` output and honest `INCONCLUSIVE` verdicts before the
  profile registry grows sustained-bandwidth thresholds.
- Future CLI/report surfaces should keep one stable machine-readable object model
  across `json` and `yaml`, with human table output as a projection layer.
- Future Intel/Apple adapter work.
- Possible later review of scheduler/runtime integration helpers after the core observability layer is mature.

Session workflow
- Start by reading `app_spec.txt`, `feature_list.json`, `claude-progress.txt`, and `docs/agent-playbook.md`.
- Run `./init.sh` before making changes unless there is a clear reason not to.
- Prefer one discrete feature or validation item per session.
- When work is done, update `feature_list.json` status/evidence, append a short note to `claude-progress.txt`, and keep tests green.
